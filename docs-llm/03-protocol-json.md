# 03. Протокол LLM ↔ сервер: JSON в тексте (без function-calling)

> Сводный индекс: [README.md](./README.md) · Конфиг: [02-config-providers](./02-config-providers.md) ·
> Валидатор: [04-validate-subcommand](./04-validate-subcommand.md) · Цикл: [05-agent-loop-limits](./05-agent-loop-limits.md).

## 1. Формат ответа LLM

**Решение (зафиксировано):** нативный function-calling НЕ используется — целевые
модели локальные GGUF и могут не поддерживать tool-вызовы. LLM отвечает **обычным
текстовым сообщением**, из которого сервер извлекает ПЕРВЫЙ `{...}` блок и парсит его
как JSON:

```jsonc
{ "action": "<имя действия>", "args": { ... } }     // + опционально:
{ "action": "run_generation", "args": {...}, "thought": "текст рассуждения" }
```

- `action` — строка, одно из шести имён (§4–§9).
- `args` — объект; для `run_generation` может быть пустым `{}` (§4), для остальных
  действий — с обязательными полями по схемам (§5–§9).
- `thought` — **опциональное** поле, свободный текст: комментарий/рассуждение LLM.
  Сервер не интерпретирует его; записывает в журнал сессии (поле `summary` шага,
  [05](./05-agent-loop-limits.md) §4), чтобы лог в UI объяснял «почему LLM это делает».

Текст ДО и ПОСЛЕ JSON-блока игнорируется. Один ответ = ровно одно действие за шаг.

## 2. Извлечение и разбор блока (серверная часть, `app/server/llm/protocol.ts`)

1. Поиск ПЕРВОГО вхождения `{` в сообщении; от него — балансированный пролёт по
   скобкам до соответствующего `}` (учитываются ВЛОЖЕННЫЕ скобки и строковые
   литералы с экранированием `\"`). Всё до первого `{` — «предисловие», игнорируется.
2. Найденный блок → `JSON.parse`. Структура обязана быть объектом со строковым
   `action` из известного набора и объектным (или отсутствующим → `{}`) `args`.
3. **Неверный JSON / неизвестное действие / нарушение схемы аргументов** → сервер
   шлёт LLM follow-up-сообщение:

   > «Твой ответ не распознан как валидное действие. Верни строго валидный JSON в
   > формате `{"action": <имя>, "args": {...}}`. Доступные действия: run_generation,
   > read_result, correct_result, create_blockages_file, create_preset_file, finish.
   > Схемы — в системном промпте.»

   Повтор **до 2 раз**. После третьего неверного ответа сессия переходит в состояние
   `error` (сообщение об ошибке — [05](./05-agent-loop-limits.md) §3).
4. Валидный JSON, но **аргументы отвергаются сервером** (запрещённые оверрайды,
   §4; нарушения валидации маски, §6) — это НЕ ошибка протокола: повтор по п.3 НЕ
   идёт, LLM получает сообщение-ошибку с описанием проблемы и может выбрать другое
   действие на следующем шаге (лимиты цикла при этом применяются как обычно).

История сообщений сессии (паттерн OpenAI chat): `system` — системный промпт
([05](./05-agent-loop-limits.md) §3); ответы LLM — `assistant`; результаты действий
и сообщения-ошибки сервер возвращает как `user`-сообщения вида:

```text
Результат run_generation: {"file":"result-20260913-200232.txt","exitCode":0,"feasible":true, ...}
Ошибка: <текст на русском> (повтори действие с исправленными аргументами или выбери другое)
```

## 3. Общие правила валидации аргументов (все действия)

1. Типы по схемам §4–§9; лишние поля в `args` — **отвергаются** сообщением-ошибкой
   («неизвестные аргументы: …»), а не молча игнорируются — LLM должна увидеть, что
   её ответ принят не полностью.
2. Имена файлов (`file`, `baseFile`) — только basename существующего result-файла
   проекта (регламент имени `result-<YYYYMMDD-HHMMSS>.txt`, как в
   `app/server/workspace.ts::RESULT_NAME_RE`); пути/`../` → ошибка. Имена из списков,
   созданных ВНЕ сессии, допустимы для чтения (`read_result`) — LLM может анализировать
   и старые результаты проекта.
3. Ошибки аргументов возвращаются LLM текстом на русском (примеры — §10); UI видит их
   в логе шагов как `ok:false` с кратким summary.

## 4. `run_generation` — запуск генератора с оверрайдом параметров

```jsonc
{ "action": "run_generation",
  "args": {
    "seed": 7,                            // опционально, целое ≥ 0
    "timeBudget": 2.0,                    // опционально, число > 0 (сек) → --time-budget
    "nodeBudget": 50000,                  // опционально, целое > 0 → --node-budget
    "areaPercent": { "ком1": 20 },        // опционально: clusterId → новая доля (%)
    "blockagesFile": "blocked-llm-….txt", // опционально (LST-7): маска блокировок, созданная create_blockages_file
    "presetsFile": "preset-llm-….txt"     // опционально (LST-7): пресет, созданный create_preset_file
  } }
```

Все поля `args` опциональны; пустые `{}` = запуск спеки проекта без оверрайдов:
seed не передаётся (дефолтный seed солвера), `--time-budget` равен лимиту
`timeBudgetPerRun` прогона ([05](./05-agent-loop-limits.md) §2).

**Маски-оверрайды (LST-7):** `blockagesFile`/`presetsFile` — только **basename**
файлов, созданных инструментами [§8](#8-create_blockages_file--создание-маски-блокировок)/[§9](#9-create_preset_file--создание-пресета)
(регламенты `blocked-llm-<YYYYMMDD-HHMMSS>.txt` / `preset-llm-<…>.txt`,
`app/server/llm/actions.ts::LLM_BLOCKAGES_FILE_RE` / `LLM_PRESET_FILE_RE`), и файл
обязан существовать в каталоге проекта. Оба могут передаваться вместе.
`blockagesFile` доступен **только когда `spec.blockedFile === null`** (у пользователя
нет своей маски); `presetsFile` — всегда (при прогоне заменяет preset проекта).
При оверрайде блокировок допуск `areaPercent` проверяется от **НОВОЙ базы F**
(свободных клеток по новой маске). Сервер подставляет пути на эти файлы в
одноразовую временную копию спеки (п.3 ниже) — spec.yaml не изменяется.

**ВАЛИДАЦИЯ ОВЕРРАЙДОВ (жёсткое правило):** разрешены ТОЛЬКО `seed`, бюджеты
(`timeBudget`, `nodeBudget`), `areaPercent` в пределах заданного пользователем
tolerance от цели кластера и имена масок LLM (`blockagesFile`, `presetsFile`):

1. **areaPercent:** для кластера с целью `target = round(F · areaPercent_текущая / 100)`
   клеток допустимо новое значение только если
   `|round(F · new/100) − target| ≤ tolerance% × target`, где **tolerance = 10 %**
   (тот же порог, что правило 6 валидатора и `WARNING_THRESHOLD_PERCENT` docs/05 §6).
   Выход за допуск → ошибка: «кластер `ком1`: запрошенная доля 40% (≈90 клеток)
   выходит за допуск 10% от цели 29 клеток (разрешено ≈26–32)». Кластеров с целью 0
   оверрайд не допускается.
2. **ЗАПРЕЩЕНЫ** любые другие изменения конфигурации: `touchAll`/`fillAll`
   (критичные настройки пользователя), размер сетки (`grid.width/height`), чужие
   маски (прямые имена `blockedFile`, `presetFile` — только LLM-маски §8/§9),
   реестр типов (`types`), формы кластеров (`shape`), правила соседства и пр.
   Такие аргументы (включая любые неизвестные поля) **отвергаются сообщением-ошибкой
   для LLM**: «аргумент `touchAll` запрещён в рамках LLM-прогона: можно менять только
   seed, timeBudget, nodeBudget, areaPercent (±10% от цели кластера) и имена своих
   масок blockagesFile/presetsFile». На диск spec.yaml НЕ записывается НИЧЕГО — оверрайды
   применяются только к аргументам запуска; при `areaPercent` сервер вычисляет
   эквивалентные целевые клетки и передаёт их солверу через существующие механизмы,
   не изменяя файл спеки.
3. **Запуск** — существующий механизм генерации: `runSolver` из `app/server/generate.ts`
   (`.venv/bin/python -m space_manager place <spec> [--seed N] --time-budget <t>
   [--node-budget n] --out <file>`), через очередь проекта; timeout запуска =
   `timeBudgetPerRun + 30 c` (05 §2). CLI `place` не имеет флага оверрайда долей,
   поэтому: **без** оверрайдов запускается спека проекта как есть (`spec.yaml`,
   путь обычный); **с** `areaPercent` и/или mask-оверрайдами сервер создаёт во
   временном каталоге (вне проекта) одноразовую копию спеки с подставленными
   долями и масками: заданные LLM-маски (`blockagesFile` → `blockedFile`,
   `presetsFile` → `presetFile`) — абсолютными путями на файлы проекта, остальные
   маски резолвятся в абсолютные от каталога спеки (`spec_io._resolve_files`), и
   запускает `place` на ней.
   **Файлы проекта (spec.yaml включительно) при этом не изменяются.** Временная
   копия удаляется после запуска. Result-файл (`--out`) пишется сразу в проект под
   **стандартным именем**
   `result-<YYYYMMDD-HHMMSS>.txt` → автоматически попадает в существующую историю
   результатов проекта (селектор viewer3d, список ревизий) — никакого отдельного
   хранилища «LLM-результатов» нет.

Ответ сервера LLM: `{"file": "...", "exitCode": 0|1, "feasible": true|false,
"summary": <компактная сводка §5>}` (exit 2 не ожидается — спека уже прошла валидацию
в UI; если всё же случится, возвращается ошибка с текстом stderr).

## 5. `read_result` — чтение и анализ отчёта

```jsonc
{ "action": "read_result", "args": { "file": "result-20260913-200232.txt" } }
```

Сервер возвращает LLM:

1. **Текст отчёта** (полный, как в файле) — секции «== КАРТА ==», таблица,
   предупреждения/блок невозможности;
2. **Компактную сводку по кластерам** (JSON): по каждой строке таблицы —
   `{id, type, target, actual, deviation, status}` (статусы: ок / недостача /
   превышение, как в отчёте);
3. **Геометрию связных областей** карты (JSON): для каждого символа типа карта
   разбивается на связные компоненты по 8-окрестности; запись области —
   `{type, symbol, cells: <размер>, bbox: [x0, y0, x1, y1]}` (координаты: x —
   столбец 0..width−1 слева направо, y — ряд 0..height−1 сверху вниз).

Известное ограничение (то же, что у валидатора, [04](./04-validate-subcommand.md) §6):
два кластера одного типа, соприкасающиеся на маске, дают ОДНУ область — пер-кластерная
геометрия по маске не восстанавливается.

## 6. `correct_result` — коррекция маски на уровне клеток

```jsonc
{ "action": "correct_result",
  "args": {
    "baseFile": "result-20260913-200232.txt",
    "edits": [ {"x": 15, "y": 7, "symbol": "."}, {"x": 4, "y": 3, "symbol": "C"} ],
    "reason": "заменил островок R в коридоре на свободные клетки — устраняет недостачу"
  } }
```

LLM **МОЖЕТ корректировать result-маску на уровне клеток**. Валидация:
`baseFile` — существующий result-файл проекта; `edits` — непустой массив, координаты
в пределах сетки спеки, `symbol ∈ {*, .} ∪ символы spec.types`; `reason` — строка.

**КРИТИЧНОЕ ПРАВИЛО (зафиксировано; дублируется в системном промпте — 05 §3.2):**
> **LLM НИКОГДА не изменяет существующий файл.** Коррекция создаёт НОВЫЙ файл на
> основе исходного: сервер копирует `baseFile` под новым именем
> `result-<YYYYMMDD-HHMMSS>.txt`, применяет `edits` только к копии (замена символов в
> секции «== КАРТА ==»; таблица и остальные секции пересчитываются/обновляются в
> соответствии с маской, формат отчёта не меняется), исходный файл остаётся
> **нетронутым**.

Последовательность на сервере:

1. создать копию с новым именем; применить edits;
2. запустить **`space_manager validate <новый> --spec spec.yaml`**
   ([04](./04-validate-subcommand.md));
3. exit ≠ 0 → список нарушений возвращается LLM сообщением-ошибкой, **невалидный
   файл удаляется** (в проект и историю не попадает);
4. exit 0 → новый файл сохраняется в проект, `latestResult` метаданных обновляется
   (как при обычной генерации) → файл появляется в истории результатов и селекторе
   viewer3d; LLM получает `{"file": "<новый>", "validated": true}`.

## 7. `finish` — завершение прогона

```jsonc
{ "action": "finish",
  "args": {
    "candidates": [
      {"file": "result-20260913-200501.txt", "comment": "все кластеры в допуске, лучший баланс"},
      {"file": "result-20260914-081230.txt", "comment": "коридор уже, но комната 2 ниже цели на 6%"}
    ],
    "recommended": "result-20260913-200501.txt"      // опционально, = file одного из кандидатов
  } }
```

Завершение сессии: все варианты с оценкой/комментарием **относительно запроса
пользователя**; `recommended` — необязательная отметка «рекомендовано».
**Окончательный выбор делает ПОЛЬЗОВАТЕЛЬ в UI** (открывает кандидата в viewer3d,
сравнивает) — LLM не принимает решение за него; сервер не «подставляет» recommended
в `latestResult`.

Валидация: `candidates` непустой массив; каждый `file` — существующий result-файл
проекта (LLM может рекомендовать и допрогоновые файлы проекта, созданные ранее);
комментарии — строки; `recommended` ∈ `{c.file}`. После валидного `finish` сессия →
`done`, журнал пишется ([05](./05-agent-loop-limits.md) §4).

## 8. `create_blockages_file` — создание маски блокировок

```jsonc
{ "action": "create_blockages_file",
  "args": {
    "content": "..**\n....\n****",   // полный текст маски: ровно height строк × width символов
    "reason": "стена в углу — уменьшает свободную площадь"  // непустая строка
  } }
```

Доступно **только когда `spec.blockedFile === null`** (у пользователя нет своей маски;
иначе сервер возвращает LLM ошибку «у пользователя уже есть маска блокировок —
создание запрещено»). Валидация: `content` обязан пройти проверку размера W×H
(`maskToGrid`, строки читаются сверху вниз: y=0 — первая строка, x — слева направо);
«*» = заблокировано, любой другой символ = свободно. Успех → **НОВЫЙ файл проекта**
`blocked-llm-<YYYYMMDD-HHMMSS>.txt` (уникальность по паттерну `nextResultName`,
spec.yaml не трогается). Ответ LLM: `{"file", "blockedCells", "freeCells",
"previousFreeCells"}` + пояснение, что проценты кластеров теперь считаются от **НОВОЙ
F** (блокировки меняют базу процентов, docs/03 §2).

## 9. `create_preset_file` — создание пресета

```jsonc
{ "action": "create_preset_file",
  "args": {
    "content": "RRR....\n..CCC..\n",   // полный текст маски: ровно height строк × width символов
    "reason": "зафиксировать комнату и коридор"            // непустая строка
  } }
```

Доступно **ВСЕГДА** (при прогоне с `presetsFile` маска LLM заменяет собственный
preset проекта — это задокументировано в описании действия). Валидация: размер W×H +
**строгая проверка символов**: только «.» и символы реестра типов спеки. Успех →
**НОВЫЙ файл** `preset-llm-<YYYYMMDD-HHMMSS>.txt`. Ответ LLM:
`{"file", "regions": [{"type", "symbol", "cells", "bbox":[x0,y0,x1,y1]}]}` (связные
области через `connectedRegions`, `app/server/llm/reportParse.ts`) + напоминание, что
preset **не уменьшает F**, а задаёт неподвижные кластеры.

## 10. Формат сообщений-ошибок для LLM

Текст на русском, одна строка/абзац, структура: **что не так** + **что делать**.
Примеры (эталонные тексты для тестов):

```text
Ошибка: не удалось разобрать JSON в твоём ответе. Верни строго валидный JSON в формате {"action": <имя>, "args": {...}}.
Ошибка: аргумент `touchAll` запрещён в LLM-прогоне. Разрешены только seed, timeBudget, nodeBudget, areaPercent (±10% от цели кластера) и имена своих масок blockagesFile/presetsFile.
Ошибка: у пользователя уже есть маска блокировок (blocked.txt) — аргумент blockagesFile запрещён. Повтори run_generation без него.
Ошибка: кластер `ком2`: доля 45% (≈76 клеток) вне допуска от цели 40 (33–47 клеток). Уменьши оверрайд или используй correct_result.
Ошибка: correct_result — нарушения валидации нового файла result-20260913-200915.txt:
  1) запрещённая смежность ROOM↔WALL у клетки (17, 8);
  2) тип holl: площадь 128 против цели 130 вне допуска (±10%).
Исправь edits и повтори correct_result (исходный файл не изменяется).
```
