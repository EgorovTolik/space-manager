# 04. Python-подкоманда `space_manager validate`

> Сводный индекс: [README.md](./README.md) · Архитектура: [01-architecture](./01-architecture.md) ·
> Протокол (кто вызывает): [03-protocol-json](./03-protocol-json.md) §6 · Тесты: [07-testing-acceptance](./07-testing-acceptance.md) §3.

## 1. Назначение

Проверка result-маски **послефактум** — по готовому текстовому файлу отчёта и
спеке, БЕЗ повторного запуска солвера и БЕЗ ассайнмента клеток кластерам (в маске он
не восстанавливается, §6). Используется сервером в `correct_result`
([03](./03-protocol-json.md) §6) — после того как LLM откорректировала копию маски,
сервер обязан убедиться, что новая маска не нарушает жёсткие правила проекта, до
сохранения файла в проект и историю.

**Жёсткое ограничение:** форматы файлов `result-*.txt` / `spec.yaml` / масок НЕ
меняются — подкоманда только читает их в существующем виде (README §3).

## 2. Командный интерфейс

```bash
.venv/bin/python -m space_manager validate <result.txt> --spec <spec.yaml> [--tolerance PERCENT]
```

| Аргумент | Обязательность | Семантика |
|---|---|---|
| `<result.txt>` | да | путь к result-файлу (секция «== КАРТА ==» читается по контракту docs/06 §3) |
| `--spec <spec.yaml>` | да | спека, относительно которой проверяется маска (отсюда grid, types, rules, кластеры, пути blocked/preset) |
| `--tolerance PERCENT` | нет | допуск правила 6; дефолт **10** — см. §5.6 |

Exit-codes:

| Код | Смысл | stdout/stderr |
|---|---|---|
| `0` | маска валидна | строка «ОК: нарушений нет» (или пусто) |
| `3` | найдены нарушения | **список нарушений в stdout**, человекочитаемый (§5) |
| `2` | ошибка входных данных — не удалось прочитать/разобрать result-файл, спеку или маски | сообщение «ОШИБКА ВХОДНЫХ ДАННЫХ: …» в stderr (формат как у `place`, docs/06 §7) |

Код 3 выбран свободным существующими кодами `place` (0/1/2, docs/06 §7); подкоманда
`place` и её exit-codes не изменяются.

## 3. Ввод-вывод

Читается: секция «== КАРТА ==» result-файла (строки по y, символы по x — как в
`report.py::render_grid`: `*` — blocked, `.` — свободная, символ типа из реестра);
спека через `spec_io.load_spec` (вместе с ней — маски `blocked.txt`/`preset.txt` по
путям спеки). Пишется: только stdout/stderr; файловые артефакты НЕ создаются.

## 4. Что проверяется — и что сознательно НЕ проверяется

Проверяется ТОЛЬКО то, что проверяемо по маске карты **без ассайнмента кластеров**
(форматы файлов не дают восстановить «какая клетка какому кластеру»): перечислены
правила 1–6 (§5). **НЕ проверяются** (невозможно по маске в формате v1):

- пер-кластерные площади и формы (два соприкасающихся кластера одного типа — одна
  неразличимая область, §6);
- связность отдельных кластеров; `touchAll`; `size.min/max` на уровне кластеров;
- мягкие отклонения («недостача»/«превышение» в пределах допуска) — это не нарушения.

## 5. Правила (исчерпывающий список, порядок вывода нарушений)

Обозначения: `W×H = spec.grid.width × spec.grid.height`; символы типов —
`{t.symbol}`; F-клетки — свободные после blocked/preset.

1. **V-GRID.** Размер карты == grid W×H спеки: ровно H строк, в каждой ровно W символов.
2. **V-SYMBOL.** Все символы ∈ `{*, .} ∪ {t.symbol : t ∈ spec.types}`. (Символ `?`
   «повреждённого» отчёта — нарушение.)
3. **V-BLOCKED / V-PRESET.** Блокировки и пресеты сохранены: каждая клетка,
   заблокированная в `blocked.txt`, на маске остаётся `*`; каждая клетка
   `preset.txt` стоит на своём месте со своим символом типа (не перекроена).
4. **V-ADJACENCY.** Запрещённые пары смежности `rules.adjacency.forbidden` не
   касаются друг друга по границам связных областей разных типов: области типов A и B
   (связные компоненты символов карты, 8-окрестность — docs/04 §1) НЕ должны иметь
   клеток на расстоянии Чебышёва ≤ 1. Одинаковые типы — **всегда разрешено**
   (docs/04 §2, п.1). Проверка выполняется существующей семантикой
   `rules.adjacency_ok` (запрещена пара из `forbidden`; если в спеке задан и
   whitelist `allow` — применяется он же, как в солвере), т.е. реализация переиспользует
   `adjacency_ok`/`clusters_touch` ([§7](#7-реализация)).
5. **V-RECTANGLE.** Для типа, у которого в спеке ровно ОДИН кластер с
   `shape: rectangle`, его область на маске обязана быть полным осевым
   прямоугольником (клетки = ровно все клетки bbox; проверка — существующая
   `rules.is_rectangle`). Если таких типов нет — правило не применяется.
6. **V-AREA.** Агрегированные площади по типам: для каждого типа сравнение
   «суммарное число клеток этого типа на маске» с «суммой целей кластеров этого типа»
   (`target = round(F · areaPercent / 100)`, как в отчёте, docs/06 §4); отклонение
   **вне допуска (tolerance)** → нарушение. Допуск — см. §5.6.

### 5.6 Tolerance правила 6

В текущем формате спеки поля `tolerance` НЕТ (форматы не меняются), поэтому
валидатор берёт порог «существенного отклонения» тот же, что и отчёт солвера:
константа **`WARNING_THRESHOLD_PERCENT = 10.0`** (`space_manager/report.py`, docs/05 §6)
— дефолт **10 % от суммы целей типа**. Флаг `--tolerance PERCENT` (целое/дробное ≥ 0)
позволяет переопределить порог для ручного запуска; LLM-модуль использует дефолт.

### 5.7 Формат вывода нарушений

Каждое нарушение — одна строка `Код: что нарушено (детали)`, в конце — итог:

```text
НАРУШЕНИЕ V-ADJACENCY: типы ROOM и holl запрещены к смежности (rules.adjacency.forbidden), касаются у клетки (17, 8)
НАРУШЕНИЕ V-PRESET: клетка (2, 5): preset требует символа 'R', на маске '.'
НАРУШЕНИЕ V-AREA: тип ROOM: 94 клетки против суммы целей 106 (-11%) — вне допуска 10%
ИТОГО нарушений: 3
```

Текст человекочитаемый (stdout), на русском; LLM получает его как есть в сообщении-ошибке
([03](./03-protocol-json.md) §10).

## 6. Ограничение формата (задокументировано явно, известное ограничение v1)

Два кластера одного типа, соприкасающиеся на маске, образуют **неразличимую область**:
по тексту отчёта невозможно сказать, где «оканчивается» один кластер и начинается
другой (в маске они — одинаковый символ). Поэтому валидатор проверяет **агрегаты по
типам** (правила 4–6), а не пер-кластерные площади/формы:

- правило 5 (rectangle) применяется только к типу с ровно ОДНИМ кластером
  `shape=rectangle` — в этом случае область типа целиком и есть тот кластер;
- если у такого типа НЕСКОЛЬКО кластеров (или тип соприкасается с другими областями
  того же типа), точная проверка формы невозможна — правило к нему не применяется.

Это задокументированное ограничение v1 подзадачи LST-1; расширение (например,
многоцветные/нумерованные символы в маске) потребует изменения формата отчёта и
рассматривается отдельно.

## 7. Реализация

1. **Новый модуль** `space_manager/validate_map.py` (+ регистрация подкоманды в
   `cli.py::build_parser` — добавление, переписывание существующего кода `place`
   отсутствует). Структура: `parse_result_map(text) -> List[List[str]]` (парсер
   секции «== КАРТА ==»), `validate(spec, mask_lines) -> List[Violation]`,
   `_cmd_validate(args) -> int`.
2. **Переиспользование существующего кода** (без дублирования логики):
   - `spec_io.load_spec` / `read_blocked_file` / `read_preset_file` — загрузка спеки и масок;
   - `rules.adjacency_ok`, `rules.clusters_touch`, `rules.is_rectangle` — правила 4 и 5;
   - `report.WARNING_THRESHOLD_PERCENT` — порог правила 6;
   - расчёт целей `round(F · areaPercent / 100)` — та же формула, что таблица отчёта (docs/06 §4).
3. **Python 3.9** — жёсткое ограничение пакета: без `match`, без `X | Y` в
   аннотациях (только `typing.Optional/List/Tuple`; `from __future__ import annotations`).
4. **Тесты** — pytest в `tests/`: валидный случай + каждый сломанный кейс каждого
   правила 1–6 (детальный список — [07](./07-testing-acceptance.md) §3); фикстуры —
   мелкие маски 8×8/10×10, как в существующих тестах пакета.
