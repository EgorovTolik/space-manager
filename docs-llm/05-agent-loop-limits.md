# 05. Агентный цикл, лимиты и системный промпт

> Сводный индекс: [README.md](./README.md) · Протокол: [03-protocol-json](./03-protocol-json.md) ·
> API/UI (стоп, опрос): [06-api-ui](./06-api-ui.md) · Тесты: [07-testing-acceptance](./07-testing-acceptance.md).

## 1. Механика цикла

Сессия = системный промпт + история сообщений. На каждом шаге LLM вызывает **ОДНО
действие**, сервер выполняет его (исполнители — `app/server/llm/actions.ts`, протокол
— [03](./03-protocol-json.md)) и возвращает результат следующим сообщением истории;
шаг повторяется. Стоп цикла — по одному из условий:

1. `action = finish` (валидный, [03](./03-protocol-json.md) §7) → состояние `done`;
2. исчерпан **maxIterations** (см. §2) и LLM не завершилась;
3. истёк **totalTimeoutSec** (стеновое время сессии);
4. ошибка, которую нельзя продолжить: 3 неверных ответа протокола подряд
   ([03](./03-protocol-json.md) §2), недоступность LLM-провайдера, сбой spawn солвера →
   состояние `error`.

Остановка пользователем («Стоп») — см. §4. В любом из случаев журнал сессии
записывается/дописывается (§5).

```
prompt+конфиг ──► [системный промпт, 05 §3]
                    │
        ┌───────────▼───────────┐   до maxIterations и totalTimeoutSec
        │ шаг: LLM → {action,args}│
        ├───────────┬───────────┘
        ▼           ▼            ▼             ▼
  run_generation read_result correct_result finish
  (runSolver,    (отчёт+сводка) (+validate,   ──────► done
   очередь)      +геометрия)   новый файл)         журнал §5
        │           │            │
        └───────────┴────────────┘
              результат → в историю сообщений → следующий шаг
```

## 2. Лимиты (дефолты; задаются пользователем в UI, 06 §2)

| Лимит | Дефолт | Семантика |
|---|---|---|
| `maxIterations` | **5** | максимум **запусков генератора (`run_generation`) + коррекций (`correct_result`)** за прогон. Счётчик увеличивается только на этих двух действиях; `read_result` и сообщения-ошибки протокола счётчик не двигают. После исчерпания любое действие, кроме `finish`, отвергается сообщением: «Лимит шагов исчерпан (5). Вызови finish с лучшими кандидатами.» Если LLM игнорирует требование — после следующего неверного шага сессия → `stopped`. |
| `timeBudgetPerRun` | **2.0** с | значение `--time-budget` каждого запуска генератора в прогоне (если LLM не передала свой `timeBudget` в аргументах — 03 §4). Timeout самого child-процесса = `timeBudgetPerRun + 30 c` (защита от зависшего солвера; SIGKILL как в существующей генерации). |
| `nodeBudget` | дефолт солвера | флаг `--node-budget` НЕ передаётся, если LLM его не указала (дефолт `DEFAULT_NODE_BUDGET` из `space_manager/solver.py`). |
| `totalTimeoutSec` | **180** | стеновое время всей сессии (от старта до finish/стопа). По исчерпании — принудительная остановка, состояние `stopped`, причина «превышен общий лимит времени». |

Все три значения валидируются при старте: целые/числовые > 0; `maxIterations` ≤ 50
(защита от опечатки «500»); некорректные → 400 `LLM_INVALID_BODY` (06 §1.2).

## 3. Системный промпт (на русском)

Собирается сервером на старте сессии (`app/server/llm/session.ts`). Структура —
четыре пронумерованные части:

### 3.1 Часть 1 — «Описание системы»

Что такое space-manager: веб-инструмент размещения замкнутых кластеров (комнаты,
коридоры и т.п.) на пиксельной сетке по YAML-спекации; генератор **детерминирован**
(одинаковые входные данные + seed → одинаковый result); LLM встроена в веб-редактор
для **подбора параметров генерации** (seed, бюджеты, доли кластеров в пределах допуска)
и **оценки/корректировки размещений**; запуск и сохранение файлов выполняет сервер —
LLM только принимает решения по данным.

### 3.2 Часть 2 — «Возможности»

Список четырёх действий с ТОЧНОЙ схемой аргументов (как в [03](./03-protocol-json.md) §4–§7)
и ОГРАНИЧЕНИЯМИ:

- можно менять только `seed`, `timeBudget`, `nodeBudget` и `areaPercent` (±10 % от цели кластера);
- **запрещено**: `touchAll` (критичная настройка пользователя), размер сетки, маски, типы, формы — такие аргументы сервер отвергнет;
- **коррекция = только НОВЫЙ файл на основе исходного** (КРИТИЧНОЕ ПРАВИЛО: LLM никогда не изменяет существующий файл; сервер сам создаёт копию под новым именем и проверяет её `validate`);
- ответ всегда — **один валидный JSON** `{"action": <имя>, "args": {...}}` + опциональное поле `thought` (комментарий/рассуждение, попадает в лог прогона);
- завершение — только через `finish` с кандидатами и комментариями; окончательный выбор результата делает пользователь.

### 3.3 Часть 3 — «Исходная конфигурация»

Полный **spec.yaml** проекта + маски **blocked/preset**:

- если сетка **≤ 2000 клеток** (`grid.width × grid.height`) — маски вставляются
  **сырым текстом** (как есть в файлах);
- иначе — **компактная сводка**: число F-клеток (свободных после blocked/preset),
  число заблокированных клеток, пресеты с позициями и размерами (id/тип, bbox,
  клетки). spec.yaml всегда вставляется полным текстом.

### 3.4 Часть 4 — «Запрос пользователя»

Текст промпта из UI дословно + желаемый результат (формулировка: «выполни запрос,
работая в рамках лимитов и ограничений; по завершении вызови finish»).

## 4. Состояния и остановка

Состояния сессии: **`running` → `done` | `stopped` | `error`** (терминальные —
последние три).

| Переход | Причина |
|---|---|
| → `done` | валидный `finish` (§1.1) |
| → `stopped` | «Стоп» от пользователя; totalTimeoutSec; исчерпан maxIterations без finish |
| → `error` | 3× неверный протокол, провайдер недоступен, сбой spawn солвера, прочие необработанные сбои цикла |

**Остановка («Стоп»)** — тот же механизм, что в существующей генерации: сервер
устанавливает **стоп-флаг** сессии и делает **SIGKILL child-процесса**, если он в этот
момент запущен (`runSolver` уже умеет убивать процесс по таймауту — сигнал отправляется
в тот же механизм). Флаг проверяется: (а) **между шагами** цикла (перед каждым новым
LLM-вызовом), (б) **после каждого запуска** солвера/валидатора. При остановке во время
запуска частичный result-файл удаляется (паттерн обычной генерации,
`app/server/index.ts` 6.10); сессия → `stopped`, журнал дописан.

## 5. Журнал прогонов (llm-sessions)

Каждая сессия — файл **`workspace/<slug>/llm-sessions/<YYYYMMDD-HHMMSS>.json`**
(имя = id сессии, часы системы проекта; одна активная сессия на проект → коллизий имён
нет). Формат (исчерпывающий):

```jsonc
{
  "prompt": "текст запроса пользователя",
  "modelId": "eac-mac-ai/Qwen3.6-35B-A3B-UD-Q6_K.gguf",
  "limits": { "maxIterations": 5, "timeBudgetPerRun": 2.0, "totalTimeoutSec": 180 },
  "iterations": [
    { "n": 1, "action": "run_generation", "args": {"seed": 7}, "ok": true,
      "summary": "thought: пробуем новый seed; файл result-20260913-200232.txt (exit 0)" }
  ],
  "candidates": [ { "file": "result-20260913-200232.txt", "comment": "..." } ],
  "recommended": "result-20260913-200232.txt",          // опционально (без finish — отсутствует)
  "status": "done",                                     // running | done | stopped | error
  "startedAt": "2026-09-13T20:02:32.000Z",
  "finishedAt": "2026-09-13T20:04:07.000Z"              // null, пока running
}
```

Правила записи: файл создаётся на старте (`status:"running"`), дописывается при
терминальном состоянии; `iterations` — все шаги (включая `ok:false` с причиной);
`summary` — краткая строка на русском (thought LLM + результат действия).
**Панель результатов редактора показывает последнюю сессию** проекта (06 §2.4):
состояние, лимиты, лог шагов, кандидатов; полный список — `GET .../llm-sessions` (06 §1).

## 6. Инварианты сессии

1. Одна активная LLM-сессия на проект (очередь проекта; вторая попытка старта →
   409 `LLM_SESSION_ACTIVE`, 06 §1).
2. Result-файлы прогона имеют стандартные имена `result-<ts>.txt` и попадают в общую
   историю результатов — отдельного каталога для «LLM-результатов» НЕТ.
3. Файлы проекта во время прогона **не изменяются**: `areaPercent`-оверрайд применяется
   через одноразовую временную копию спеки вне проекта (03 §4 п.3), бюджеты/seed —
   аргументами запуска; `correct_result` пишет только новые файлы (03 §6).
4. Лимиты фиксируются в журнале на момент старта и в ходе прогона не меняются.
