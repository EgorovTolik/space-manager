# 07. Тесты и приёмка

> Сводный индекс: [README.md](./README.md) · Все решения серии: README §2.

## 1. Общие принципы

- Паттерны существующих тестов проекта повторяются: Node — vitest в `app/tests/`
  (`createApp()` без listen, инъекция `now`/`pythonBin`, как docs-unified 05 §1);
  Python — pytest в `tests/`; редактор — vitest unit + playwright e2e с **мок-API**
  (паттерны `editor/tests/e2e/helpers.ts`: `mockProject`, перехват `/api/*`).
- Реальный солвер используется только там, где это зафиксировано (§2.2, §3);
  везде, где достаточно фейка, — фейк (детерминизм и скорость CI).
- Фейковый LLM: локальный HTTP-сервер (в пределах теста), реализующий
  `POST /v1/models` и `POST /v1/chat/completions`; ответы **scripted** (список
  заготовленных строк, выдаётся по порядку вызовов) — позволяет детерминированно
  прогонять весь протокол без настоящей модели.

## 2. Node/TS-тесты (`app`)

### 2.1 Unit

| Модуль | Что тестируется (кейсы) |
|---|---|
| Парсер JSON-протокола (`llm/protocol.ts`) | валидный `{action,args}`; блок с `thought`; мусор до/после блока; **вложенные скобки** в args и в строках; неверный JSON; пустое сообщение; неизвестное action; два блока — берётся ПЕРВЫЙ; повтор follow-up: 2 повтора → ошибка сессии |
| Валидатор оверрайдов (`llm/actions.ts`) | `areaPercent` **внутри** tolerance от цели — проходит (границы включительно); **вне** tolerance — ошибка-сообщение; кластер с целью 0; запрещённые поля: `touchAll`, `grid`, маски, `types`, `shape` — каждое по отдельности → ошибка; неизвестное поле в args; seed/nodeBudget/timeBudget — типы и границы |
| Конфиг-лоадер (`llm/config.ts`) | корректный конфиг; файл отсутствует → `configured:false`; не JSON; пустые `providers`/`apiKey`; `defaultModel` с неизвестным provider; чтение при каждом обращении (hot-reload без рестарта) |
| Модель-дискавери (`fetch` mock) | успешный `/v1/models` → отсортированный список; кэш TTL ~60 c (второй вызов без сети); сбой при наличии кэша → stale-кэш; сбой без кэша → `models: []`; labels подставляются по `<provider>/<model>` |

### 2.2 Integration

1. **Полный цикл**: фейковый LLM со scripted-ответами
   `run_generation {seed:7}` → `read_result` → `finish {candidates, recommended}` +
   **реальный Python-солвер** (`.venv/bin/python`) на маленькой спеке (паттерн
   docs-unified 05: временный workspace, маленькая сетка). Проверки: result-файл с
   именем `result-<ts>.txt` создан и валиден по формату; `GET llm-status` → `done`;
   кандидаты совпадают со scripted-ответом.
2. **Цикл с коррекцией**: scripted `correct_result` (один edit, валидный) → новый
   файл создан, **исходный байт-в-байт нетронут** (сравнение до/после), `validate`
   вызван (фейк/реальный); затем `finish`.
3. **Оверрайды в цикле**: LLM запрашивает запрещённый аргумент → следующий scripted
   ответ — исправленный; в логе сессии шаг с `ok:false` и причиной.
4. **Остановка «Стопом» и отсутствие жёсткого таймаута**: (а) прогон длиннее 180
   «стенковых» секунд по DI-часам НЕ останавливается (totalTimeoutSec убран, LST-7);
   (б) `POST llm-stop` во время реального запуска солвера → SIGKILL, частичный файл
   удалён, `stopped`; (в) стагнация: фейковый LLM зациклен на одном `run_generation`
   → 3 идентичных шага подряд → авто-`done` с `note` и кандидатами из созданных файлов
   (или `stopped`, если файлов нет).
5. **Формат журнала**: содержимое `llm-sessions/<ts>.json` сверяется со схемой 05 §5
   (поля, порядок, `limits.{maxIterations,timeBudgetPerRun}` без totalTimeoutSec,
   `iterations[].{n,action,args,ok,summary}`, terminal-status, времена, опциональный `note`).
6. **Очередь**: вторая `POST llm-generate` при активной сессии → 409
   `LLM_SESSION_ACTIVE`; после завершения — старт возможен.

## 3. Python-тесты (pytest, `tests/test_validate_*.py`)

Подкоманда `validate` ([04](./04-validate-subcommand.md)): **валидный случай** +
**каждый сломанный кейс каждого правила**:

| Правило | Сломанный кейс(ы) | Ожидаемо |
|---|---|---|
| V-GRID | карта короче/длиннее на ряд; строка неверной длины | exit 3, `НАРУШЕНИЕ V-GRID` |
| V-SYMBOL | чужой символ (напр. `X`); `?` | exit 3, `V-SYMBOL` с координатой |
| V-BLOCKED / V-PRESET | заблокированная клетка стала типом; preset-клетка перекроена (`.` или другой символ) | exit 3, `V-BLOCKED` / `V-PRESET` |
| V-ADJACENCY | области двух типов из `forbidden` касаются по ортогональной границе; по диагонали (8-окрестность!) | exit 3, `V-ADJACENCY`; отрицательный кейс: одинаковые типы соприкасаются — **не** нарушение |
| V-RECTANGLE | тип с одним кластером `shape=rectangle`: область с выемкой; валидный полный прямоугольник — не нарушение; тип с ДВУМЯ rectangle-кластерами — правило не применяется (§6 04) | exit 3 / 0 по кейсам |
| V-AREA | площадь типа на 11 % меньше суммы целей (вне допуска); ровно на границе 10 % — **не** нарушение; `--tolerance` переопределяет порог | exit 3 / 0 / зависит от флага |

Дополнительно: exit 2 на несуществующих result/spec; комбинация нескольких нарушений →
все в stdout + «ИТОГО нарушений: N». Фикстуры — мелкие маски 8×8/10×10 (паттерн
существующих тестов пакета).

## 4. Редактор (`editor`) и сквозной e2e

1. **Unit (vitest)**: чистые модули панели — форматирование лога шагов, выбор модели
   по `defaultModel`, валидация полей лимитов (пусто = дефолты 5/2.0/180), строки
   i18n `ru.llm.*` существуют для всех элементов (паттерн существующих unit-тестов).
2. **E2E (playwright, мок-API)** — новые спеки в `editor/tests/e2e/` по паттернам
   `05-generate.spec.ts`:
   - «LLM не настроен»: мок `GET /api/llm/providers` → `{configured:false}` → строка
     «LLM не настроен», элементы недоступны; обычная кнопка «⚡ Генерировать размещение»
     работает как раньше (регрессия);
   - запуск: выбор модели, промпт, «Запустить» → мок 202 `{sessionId}` → опрос статуса
     (мок: running → done с candidates) → лог шагов и список кандидатов с бейджем
     «рекомендовано» и ссылкой `/viewer3d/?project=<slug>&result=<file>`;
   - «Стоп»: мок активного прогона → клик «Стоп» → `POST llm-stop` ушёл, UI показывает
     `stopped`.
3. **Сквозной e2e**: реальный app-сервер (`createApp` на тестовом порту) + фейковый LLM
   (scripted run → read → finish) + playwright: полный сценарий «промпт → прогон →
   кандидаты» через настоящий API (без мока `/api/*`).

## 5. Критерии приёмки подзадачи LST-1

1. **Доки**: каталог `docs-llm/` покрывает ВСЕ восемь зафиксированных решений
   (README §2) без противоречий с `docs/`, `docs-unified/`, `docs-editor/`,
   `docs-viewer3d/`; явно указано, ЧТО НЕ МЕНЯЕТСЯ (README §3): форматы result/spec,
   обычный запуск генерации, Python-солвер кроме новой подкоманды `validate`.
2. **Регрессия**: существующие тесты всех компонентов зелёные без изменений;
   `POST /api/projects/:p/generate` и формат `result-*.txt` — идентичны (сравнение
   эталонных отчётов).
3. Пункты 1–6 сводных критериев README §5 выполнены (настроенность/не настроенность,
   дискавери моделей, полный цикл с коррекцией и нетронутым исходником, pytest
   validate по таблице §3, отвержение запрещённых оверрайдов, stop).
4. **Код**: `llm.config.json` в `.gitignore`; в git — только
   `llm.config.example.json` с `apiKey: "ПРЕДСТАВЬТЕ_КЛЮЧ"`; ни один API-ключ не
   закоммичен (в т.ч. не вынесен полный ключ gl-hub в доки/примеры).
5. Python 3.9: пакет собирается и проходит pytest в `.venv` без новых зависимостей
   сверх существующих (PyYAML, pytest).
