## 1. Цель

Добавить в единый сервис **LLM-агента, который по запросу пользователя
самостоятельно подбирает параметры генерации размещения** и оценивает/корректирует
полученные result-файлы: цикл «запуск генератора → анализ отчёта → следующий запуск»
повторяется до достижения цели или исчерпания лимитов. Пользователь формулирует задачу
одним текстом («сделай коридор поменьше, комнаты ближе к целевой площади»), запускает
прогон и в итоге получает **несколько кандидатов** с комментариями LLM; окончательный
выбор делает пользователь.

Компоненты:

| Компонент | Где | Статус | Роль |
|---|---|---|---|
| LLM-модуль сервера | `app/server/llm/` (новый каталог) | **реализуется** | конфиг провайдеров, JSON-протокол, агентный цикл, валидация оверрайдов, журнал сессий |
| Python-подкоманда `validate` | `space_manager/` (новая подкоманда CLI) | **реализуется** | проверка result-маски по спеке без ассайнмента кластеров |
| Конфиг провайдеров | `llm.config.json` в корне проекта + `llm.config.example.json` в git | **создаётся** | API-ключи и модели локальных GGUF-провайдеров |
| API LLM-эндпоинты | `app/server/index.ts` (новые роуты) | **реализуется** | `/api/llm/*`, `/api/projects/:p/llm-*` |
| UI «LLM-генерация» | `editor/src/` (новый раздел + i18n) | **реализуется** | промпт, выбор модели, лимиты, лог шагов, кандидаты |

## 2. Зафиксированные решения (приняты без обсуждения)

1. **LLM-модуль живёт на сервере** (`app/server/llm/`), не в браузере: API-ключи
   провайдеров не должны попадать во фронт; цикл «запуск генератора → анализ →
   следующий запуск» держится рядом с существующей очередью генераций. Редактор —
   только UI (см. [01](./01-architecture.md) §2).
2. **Протокол JSON-в-тексте** без нативного function-calling (целевые модели —
   локальные GGUF): LLM отвечает сообщением, из которого сервер извлекает ПЕРВЫЙ
   `{...}` блок вида `{"action": <имя>, "args": {...}}` (+ опциональное `thought`).
   Четыре действия: `run_generation`, `read_result`, `correct_result`, `finish` —
   с точными схемами аргументов и валидацией оверрайдов
   ([03-protocol-json](./03-protocol-json.md)).
3. **Конфигурация провайдеров** — файл `llm.config.json` **в корне проекта**, в git —
   только `llm.config.example.json` (`apiKey: "ПРЕДСТАВЬТЕ_КЛЮЧ"`); модели —
   авто-опрос `{url}/v1/models` с кэшем TTL ~60 c; нет конфига → «LLM не настроен»,
   остальной сервис работает как раньше ([02-config-providers](./02-config-providers.md)).
4. **Python-подкоманда `validate`** — проверка result-маски по спеке, только то, что
   проверяемо БЕЗ ассайнмента кластеров (6 правил); форматы файлов не меняются;
   Python 3.9 ([04-validate-subcommand](./04-validate-subcommand.md)).
5. **Агентный цикл с лимитами**: maxIterations = 5, timeBudgetPerRun = 2.0 c,
   totalTimeoutSec = 180 (дефолты, задаются в UI); состояния running → done | stopped
   | error; «Стоп» = флаг + SIGKILL child-процесса; журнал
   `workspace/<slug>/llm-sessions/<ts>.json` ([05-agent-loop-limits](./05-agent-loop-limits.md)).
6. **Системный промпт на русском** — 4 части: описание системы, возможности (схемы
   действий + ограничения), исходная конфигурация (spec.yaml + маски, сырьём при
   ≤ 2000 клеток, иначе сводка), запрос пользователя ([05](./05-agent-loop-limits.md) §3).
7. **API и UI**: пять LLM-эндпоинтов в существующих паттернах `app/server/index.ts`
   (ApiError); опрос статуса раз в ~1.5 c (вариант «б», SSE НЕ делать); новый раздел
   «LLM-генерация» в редакторе рядом с кнопкой «⚡ Генерировать размещение», которая
   ОСТАЁТСЯ без изменений; i18n — `ru.ts` ([06-api-ui](./06-api-ui.md)).
8. **Тесты**: unit (парсер протокола, валидатор оверрайдов, конфиг-лоадер,
   модель-дискавери), integration с фейковым LLM-сервером + реальным Python-солвером,
   pytest `validate` (валидный случай + каждый сломанный кейс каждого правила),
   editor unit + e2e с мок-API, сквозной e2e ([07-testing-acceptance](./07-testing-acceptance.md)).

## 3. ЧТО НЕ МЕНЯЕТСЯ (жёсткое ограничение)

- **Форматы файлов** `result-*.txt` и `spec.yaml` (и `blocked.txt`/`preset.txt`) —
  без изменений: ни солвер, ни LLM-модуль, ни валидатор не добавляют ни одной секции
  или поля. Контракт формата отчёта — как зафиксирован в `docs/06-io-and-reporting.md`
  и [ТЗ viewer3d 02](../docs-viewer3d/02-input-parser.md) §1.
- **Обычный запуск генерации** — `POST /api/projects/:p/generate` (кнопка «⚡
  Генерировать размещение» в редакторе) работает ровно как сейчас, без LLM;
  LLM-прогон использует тот же механизм (`runSolver`, очередь проекта), а не новый.
- **Python-солвер** `space_manager/` — не изменяется, КРОМЕ добавления новой
  подкоманды `validate` (решение 4). Подкоманда `place`, её флаги и exit-codes
  (docs/06 §7) не меняются.
- **viewer3d** — без изменений: кандидаты LLM открываются в нём через существующий
  URL `/viewer3d/?project=<slug>&result=<file>` (новые result-файлы автоматически
  попадают в селектор ревизий, т.к. имеют стандартное имя `result-<ts>.txt`).
- **Существующие API-эндпоинты** `app/` — только добавление новых `/api/llm*`;
  существующие не переопределяются.

## 4. Как запускать (итоговый пользовательский сценарий)

```bash
# 1. конфиг LLM (один раз; шаблон в репозитории):
cp llm.config.example.json llm.config.json   # и заполнить apiKey

# 2. сборка фронтендов (по одному разу после изменений):
cd editor && npm install && npm run build    # → editor/dist

# 3. запуск единого сервиса:
cd app && npm start                          # http://localhost:4080
```

Пользователь: редактор `/editor` → выбирает проект → раздел «LLM-генерация» →
промпт + модель + лимиты → «Запустить» → наблюдает лог шагов (опрос ~1.5 c) →
по завершении видит список кандидатов с комментариями LLM и отметкой «рекомендовано» →
открывает нужный в viewer3d (`/viewer3d/?project=<slug>&result=<file>`).

## 5. Сводные критерии приёмки проекта

Подробная декомпозиция — [07-testing-acceptance](./07-testing-acceptance.md) §4.

1. `GET /api/llm/providers` без `llm.config.json` → `{configured:false}`; в редакторе
   раздел «LLM-генерация» показывает «LLM не настроен», кнопки недоступны; весь
   остальной сервис (проекты, генерация, viewer3d) работает как раньше.
2. С `llm.config.json`: список моделей каждого провайдера загружается из
   `{url}/v1/models` (кэш ~60 c); UI показывает выпадающий список
   «provider/model» с дефолтом `eac-mac-ai/Qwen3.6-35B-A3B-UD-Q6_K.gguf`.
3. Полный прогон (интеграция: фейковый LLM + реальный солвер): цикл
   run_generation → read_result → finish создаёт результатные файлы с именами
   `result-<ts>.txt`, пишет `llm-sessions/<ts>.json` заданного формата, UI показывает
   лог и кандидатов; исходный result-файл после `correct_result` остаётся нетронутым.
4. `python -m space_manager validate <result.txt> --spec spec.yaml`: exit 0 на
   валидной маске; ненулевой код + человекочитаемый список нарушений на каждом из 6
   правил (по тестам [07](./07-testing-acceptance.md) §3).
5. Запрещённые оверрайды (`touchAll`, размер сетки, маски, типы, формы) отвергаются
   сервером сообщением-ошибкой для LLM; `areaPercent` вне tolerance от цели — тоже.
6. «Стоп» во время прогона: флаг + SIGKILL child-процесса, сессия → `stopped`,
   журнал завершён. Все unit/e2e-тесты по [07](./07-testing-acceptance.md) зелёные.

## 6. Словарь

| Термин | Значение |
|---|---|
| **LLM-модуль** | серверный код `app/server/llm/` — конфиг, протокол, цикл, валидация оверрайдов |
| **провайдер** | OpenAI-совместимый HTTP-сервер модели (GGUF), запись `providers.<id>` в `llm.config.json` |
| **модель** | строка вида `<provider>/<modelId>`, например `eac-mac-ai/Qwen3.6-35B-A3B-UD-Q6_K.gguf` |
| **сессия (прогон)** | один LLM-прогон по запросу пользователя; запись в `llm-sessions/<ts>.json` |
| **шаг (iteration)** | один цикл «LLM отвечает → сервер выполняет одно действие → результат обратно» |
| **действие (action / инструмент)** | `run_generation`, `read_result`, `correct_result`, `finish` ([03](./03-protocol-json.md)) |
| **оверрайд** | временное изменение параметров генератора в рамках одного прогона: seed/бюджеты — аргументы CLI; `areaPercent` — одноразовая временная копия спеки вне проекта (03 §4); spec.yaml проекта НЕ изменяется |
| **tolerance** | допуск отклонения: 10 % от цели кластера (порог `WARNING_THRESHOLD_PERCENT`, docs/05 §6) — граница разрешённых оверрайдов и порог правила 6 валидатора |
| **кандидат** | result-файл, представленный LLM в `finish` с комментарием; выбор делает пользователь |
