# 02. Рабочее пространство и API единого сервиса

> Сводный индекс: [../docs-unified/README.md](./README.md) · Архитектура:
> [01-architecture](./01-architecture.md) · UI менеджера: [03-manager-ui](./03-manager-ui.md)

## 1. Раскладка workspace

```
<root>/workspace/                    ← корень (env SPACEMGR_WORKSPACE); создаётся сервером при старте; в .gitignore
└── <name>/                          ← проект; имя = slug [a-z0-9_-]{1,40}; каталог = имя проекта
    ├── project.json                 ← служебные метаданные (ИСКЛЮЧАЕТСЯ из архива)
    ├── spec.yaml                    ← спекация размещения (формат — docs/03-placement-spec.md)
    ├── blocked.txt                  ← маска блокировок (каноническое имя)
    ├── preset.txt                   ← предзаполненная карта (каноническое имя)
    ├── result-20260913-120000.txt   ← ревизии генераций: каждый запуск = НОВЫЙ файл
    ├── result-20260913-131504.txt
    └── preview/                     ← PNG-снапшоты viewer3d (ИСКЛЮЧАЕТСЯ из архива)
        ├── preview-20260913-132001.png
        └── preview-20260913-140512.png
```

Правила:

- `<root>` — родитель каталога `app/` (корень репозитория). В корне проекта
  **добавляется строка в `.gitignore`:** `workspace/` (репозиторный файл меняется
  оркестратором вне `docs-unified/` — чек-лист реализации, см. [05](./05-testing-acceptance.md) §6 п.1).
- Сервер создаёт `workspace/` при старте; поддиректории проектов создаются только
  через API. Файлы вне структуры (посторонние) в списке файлов проекта НЕ фигурируют,
  но и не удаляются при удалении проекта (удаляется весь каталог рекурсивно).
- Канонические имена `spec.yaml`/`blocked.txt`/`preset.txt` — фиксированы; редактор
  всегда работает именно с ними (см. [04](./04-integrations.md) §2).

## 2. Формат `project.json`

```json
{
  "id": "3f2c1b6e-8a4d-4c1e-9f0a-1b2c3d4e5f60",
  "name": "demo-project",
  "createdAt": "2026-09-13T12:00:00.000Z",
  "updatedAt": "2026-09-13T13:15:04.210Z",
  "latestResult": "result-20260913-131504.txt"
}
```

| Поле | Тип | Правило |
|---|---|---|
| `id` | string (UUID v4) | генерируется при создании (`crypto.randomUUID()`), неизменяем |
| `name` | string (slug) | = имя каталога; меняется только через rename (атомарно: `fs.rename` + запись поля) |
| `createdAt` | string (ISO 8601, UTC) | время создания, неизменяемо |
| `updatedAt` | string (ISO 8601, UTC) | обновляется ЛЮБЫМ изменением проекта (создание/переименование/сохранение файлов/генерация/preview) |
| `latestResult` | string \| null | имя последнего созданного файла `result-*`; `null`, пока генераций не было. Обновляется только успешной (exit 0/1) генерацией |

Запись — атомарная: во временный файл `<name>.tmp` + `fs.rename`. Повреждённый
`project.json` (не-JSON) → проект в списке помечается флагом `corrupted: true`,
действия кроме DELETE недоступны (ошибка `PROJECT_CORRUPTED` 500).

## 3. Имена и имена файлов

### 3.1 Slug проекта

Регулярное выражение: `^[a-z0-9_-]{1,40}$`. Дополнительно запрещены значения `.` и
`..` (регламент уже отсекает) и имена, совпадающие с существующими каталогами
workspace (case-sensitive на Linux/macOS APFS по умолчанию).

### 3.2 Форматы имён файлов

| Класс | Регулярное выражение | Пример |
|---|---|---|
| Ревизия результата | `^result-\d{8}-\d{6}(-\d+)?\.txt$` | `result-20260913-131504.txt`, при коллизии в ту же секунду — `result-20260913-131504-1.txt` |
| Предпросмотр | `^preview-\d{8}-\d{6}(-\d+)?\.png$` | `preview-20260913-140512.png` |
| Произвольный файл проекта (чтение) | `^[A-Za-z0-9._-]+$` и без подстроки `..`, не начинается с `.` | `spec.yaml`, `blocked_basic.txt` |

Timestamp — локальное время, формат `YYYYmmdd-HHMMSS` — **тот же**, что у CLI
(`spaec_manager/cli.py::default_result_name`) и viewer3d (`snapshotFileName`).

## 4. Шаблон нового проекта (создание через `POST /api/projects`)

Сервер создаёт каталог и ЧЕТЫРЕ файла. Содержимое зафиксировано побайтово
(шаблон обязан проходить валидацию редактора — коды V-* из docs-editor/05, — и
успешно генерироваться солвером).

### 4.1 `spec.yaml` (побайтовый эталон)

```yaml
grid:
  width: 20
  height: 20
blockedFile: blocked.txt
presetFile: preset.txt
types:
  ROOM: { symbol: "R", name: Комната }
rules:
  connectivity: 8
  adjacency:
    forbidden: []
    allow: null
  size:
    min: null
    max: null
  convexity:
    weight: soft
  fillAll: false
  touchAll: false
clusters:
  - id: room1
    type: ROOM
    areaPercent: 100
    shape: free
```

Обоснование полей: формат — `docs/03-placement-spec.md` §1 (стиль эталона
`examples/spec_basic.yaml`); `areaPercent: 100` + `shape: free` + один тип →
единственный кластер занимает всю сетку, размещение тривиально возможно (exit 0);
маски указаны каноническими именами (`dumpSpec` редактора пишет basename без `./`,
`load_spec` Python резолвит их от каталога спеки — `spaec_manager/spec_io.py`).

### 4.2 `blocked.txt` и `preset.txt` (побайтовый эталон)

Каждый файл: ровно 20 строк по 20 символов `.` + завершающий `\n`:

```
....................
....................   ← повтор строки, всего 20 раз
....................
```

**Почему не пустые файлы:** парсер масок редактора (`editor/src/lib/maskText.ts::
maskFileDims`) требует непустую прямоугольную сетку — пустой файл даёт ошибку
`V-MASK-DIM`. Строка из точек — каноническая форма свободной клетки по
`dumpMask` (round-trip «загрузил → сохранил» побайтово идентичен).

### 4.3 `project.json`

По §2 с `latestResult: null`, `createdAt = updatedAt = now`.

## 5. Общий формат ответов и коды ошибок

Успешные ответы — JSON (`text/plain` — только отдача содержимого файлов/картинок).
Ошибки — всегда:

```json
{ "error": "<CODE>", "message": "<человекочитаемое сообщение на русском>" }
```

| HTTP | Код | Когда |
|---|---|---|
| 400 | `INVALID_NAME` | slug/имя файла не проходит регламент §3; тело без обязательных полей |
| 400 | `BAD_ZIP` | загрузок не распаковывается / в архиве нет `spec.yaml` / вредоносные имена записей |
| 404 | `PROJECT_NOT_FOUND` | проекта `<name>` нет в workspace |
| 404 | `FILE_NOT_FOUND` | файла нет в каталоге проекта |
| 409 | `PROJECT_EXISTS` | проект с таким именем уже существует (создание/rename/import) |
| 413 | `PAYLOAD_TOO_LARGE` | тело > 10 МБ (лимит `express.raw`) |
| 422 | `SOLVER_INPUT` | солвер завершился с exit 2 (ошибка входных данных); `message` = текст stderr |
| 500 | `WORKSPACE_UNAVAILABLE` | workspace не создаётся/недоступен |
| 500 | `PROJECT_CORRUPTED` | `project.json` не читается как JSON |
| 504 | `SOLVER_TIMEOUT` | генерация > 60 с (процесс убит, частичный файл удалён) |

Все обработчики обёрнуты в единый error-middleware (паттерн `editor/server/index.ts`).

## 6. Эндпоинты (префикс `/api`)

`<p>` ниже = slug проекта. Время в ответах — ISO 8601 UTC. Сортировка списков
проектов/файлов фиксирована и детерминирована.

### 6.1 `GET /api/health`

Ответ 200: `{"status":"ok","version":"<версия app/package.json>"}` — как у editor/viewer3d.

### 6.2 `GET /api/projects` → список проектов

Ответ 200:

```json
{
  "projects": [
    {
      "id": "3f2c1b6e-…", "name": "demo-project",
      "createdAt": "2026-09-13T12:00:00.000Z", "updatedAt": "2026-09-13T13:15:04.210Z",
      "latestResult": "result-20260913-131504.txt",
      "sizeBytes": 48211, "resultsCount": 3, "previewsCount": 2
    }
  ]
}
```

`sizeBytes` — сумма размеров ВСЕХ файлов проекта (включая `preview/`);
`resultsCount`/`previewsCount` — числа файлов по регламентам §3.2. Порядок:
`updatedAt` по убыванию, при равенстве — `name` по возрастанию. Пустой workspace →
`{"projects": []}`.

### 6.3 `POST /api/projects` → создание проекта

Запрос: `{"name": "demo-project"}` (иначе 400 `INVALID_NAME`).
Сервер: проверка slug → проверка отсутствия каталога → создание структуры §4 →
запись `project.json`. Ответ **201**:

```json
{ "project": { "id": "…", "name": "demo-project", "createdAt": "…", "updatedAt": "…", "latestResult": null } }
```

Ошибки: 400 `INVALID_NAME`; 409 `PROJECT_EXISTS` («Проект с именем «x» уже существует»).

### 6.4 `PATCH /api/projects/<p>/rename` → переименование

Запрос: `{"name": "new-name"}`. Сервер: валидация нового slug →
`fs.rename(oldDir, newDir)` → запись `project.json` (name + updatedAt). Ответ 200 —
объект `project` с новым именем. Ошибки: 400 `INVALID_NAME`, 404 `PROJECT_NOT_FOUND`,
409 `PROJECT_EXISTS` (новое имя занято).

### 6.5 `DELETE /api/projects/<p>` → удаление

`fs.rm(dir, {recursive: true, force: true})`. Ответ **204** без тела. Ошибка 404.
Подтверждение — на стороне клиента (UI менеджера, [03](./03-manager-ui.md) §4).

### 6.6 `POST /api/projects/import` → импорт проекта из zip

Запрос: тело — сырые байты zip (`Content-Type: application/zip` или
`application/octet-stream`; `express.raw({limit:'10mb'})`). Необязательный query
`?name=<slug>` — имя нового проекта.

Правили распаковки (библиотека `adm-zip`):

1. Архив с **одной** верхней папкой (все записи имеют общий префикс `dir/`) —
   префикс снимается (удобно для архивов, собранных другими средствами). Плоский
   архив принимается как есть.
2. Имя проекта: `?name=` → оно; иначе имя единственной верхней папки; иначе
   `imported`. Если имя занято — автоматически `-2`, `-3`, … до свободного
   (в ответе возвращается финальное имя).
3. Записи-файлы, принимаются в проект: ровно те, чей basename проходит §3.2
   «произвольный файл» И не равен `project.json` и не лежит под `preview/` и не
   заканчивается на `.zip`. Всё остальное — в список `skipped` (с причиной).
4. Обязательна запись `spec.yaml` (после снятия префикса), иначе 400 `BAD_ZIP`:
   «В архиве не найден файл spec.yaml».
5. Защита от traversal: имя каждой записи нормализуется; абсолютные пути, `..`,
   ведущие `/` → 400 `BAD_ZIP` (архив отвергается целиком).

Сервер создаёт каталог, копирует файлы, пишет свой `project.json` (`latestResult` —
имя последнего по имени `result-*`, если есть, иначе `null`). Ответ **201**:

```json
{
  "project": { "id": "…", "name": "imported-2", "createdAt": "…", "updatedAt": "…", "latestResult": "result-20260913-104750.txt" },
  "imported": ["spec.yaml", "blocked.txt", "preset.txt", "result-20260913-104750.txt"],
  "skipped": [ { "name": "preview/preview-20260913-140512.png", "reason": "превью не импортируется" } ]
}
```

Ошибки: 400 `BAD_ZIP`, 413 `PAYLOAD_TOO_LARGE`.

### 6.7 `GET /api/projects/<p>/files` → список файлов проекта

Все обычные файлы каталога проекта **кроме** `project.json` и содержимого `preview/`
(вложенных каталогов, кроме `preview/`, в v1 не ожидается). Ответ 200:

```json
{ "files": [
  { "name": "spec.yaml",   "sizeBytes": 412,  "mtimeIso": "2026-09-13T12:00:01.000Z" },
  { "name": "blocked.txt", "sizeBytes": 420,  "mtimeIso": "2026-09-13T12:00:01.000Z" },
  { "name": "preset.txt",  "sizeBytes": 420,  "mtimeIso": "2026-09-13T12:00:01.000Z" },
  { "name": "result-20260913-131504.txt", "sizeBytes": 3165, "mtimeIso": "2026-09-13T13:15:04.210Z" }
] }
```

Порядок: редактируемые (`spec.yaml`, `blocked.txt`, `preset.txt` — по этому порядку,
если существуют), затем остальные по имени.

### 6.8 `GET /api/projects/<p>/file?name=<file>` → чтение файла

Возвращает содержимое любого регулярного файла проекта (кроме `project.json` и
`preview/*`) — в т.ч. маски с неканоническими именами, если они попали в проект
через импорт и на них ссылается спека (редактор читает имя из `spec.blockedFile/
presetFile`). Заголовки: `Content-Type: text/plain; charset=utf-8` для `.txt`/`.yaml`,
иначе `application/octet-stream`. Ошибки: 400 `INVALID_NAME`, 404 `PROJECT_NOT_FOUND` /
`FILE_NOT_FOUND`.

### 6.9 `PUT /api/projects/<p>/files` → сохранение файлов редактором

Запрос (JSON):

```json
{ "files": { "spec.yaml": "grid:\n  width: 20\n…", "blocked.txt": "…………\n", "preset.txt": "…………\n" } }
```

Семантика: **полное состояние редактируемых файлов** — указанные файлы записываются;
из канонической тройки `spec.yaml`/`blocked.txt`/`preset.txt` те, кого НЕТ в payload,
удаляются с диска (сценарий «маска удалена в редакторе» → файл исчезает, а в спеке
поле уже `null`). Имена в payload обязаны проходить §3.2 «произвольный файл», иначе
400. Ответ 200:

```json
{ "saved": ["spec.yaml", "blocked.txt"], "deleted": ["preset.txt"] }
```

`updatedAt` проекта обновляется. Ошибки: 400, 404, 413 (суммарный размер полей).

### 6.10 `POST /api/projects/<p>/generate` → запуск солвера

Запрос: пустое тело `{}` (параметры солвера в v1 не передаются — см. [05](./05-testing-acceptance.md) §7).
Сервер выполняет синхронно:

```
spawn(SPACEMGR_PYTHON, ['-m', 'spaec_manager', 'place',
        <abs>/workspace/<p>/spec.yaml', '--out', <abs>/workspace/<p>/result-<ts>.txt])
```

Правила исполнения:

- `cwd` = каталог проекта (на корректность не влияет: `load_spec` резолвит маски от
  каталога спеки — `spaec_manager/spec_io.py`, но фиксируем для детерминизма логов).
- Имя результата: `result-<YYYYmmdd-HHMMSS>.txt`; при коллизии (запуск в ту же
  секунду) — суффиксы `-1`, `-2`, … до свободного имени.
- **Hard timeout = 60 000 мс**: по срабатыванию процесс убивается (`SIGKILL`),
  частично записанный файл результата удаляется, ответ 504 `SOLVER_TIMEOUT`.
- `maxBuffer` 10 МБ; параллельные генерации одного проекта сериализуются
  in-process очередью (одна активная; остальные ждут — одноместный режим).
- Текст отчёта в ответе читается из СОЗДАННОГО ФАЙЛА (а не из stdout) — файл
  авторитетен; stdout/stderr сохраняются для диагностики и попадают в `message`
  ошибок.

Ответ **200** при exit 0 ИЛИ 1 (infeasible — это результат, не ошибка):

```json
{
  "resultFile": "result-20260913-131504.txt",
  "exitCode": 1,
  "feasible": false,
  "report": "НЕ УДАЛОСЬ РАЗМЕСТИТЬ ВСЕ КЛАСТЕРЫ.\nПричина: …\n\n== КАРТА ==\n…\n\n== ТАБЛИЦА: запрошено / фактически / отклонение ==\n…\n\n== ПРЕДУПРЕЖДЕНИЯ ==\n…"
}
```

`latestResult` в `project.json` обновляется на имя файла (и при exit 0, и при 1 —
файл создаётся в обоих случаях, `cli.py::_place`). При exit 2 → **422**
`SOLVER_INPUT`, `message` = текст stderr («ОШИБКА ВХОДНЫХ ДАННЫХ: …»), файл не
создаётся (поведение CLI), `latestResult` не меняется. Ошибки также: 404, 504.

### 6.11 `GET /api/projects/<p>/results` → список ревизий

```json
{ "results": [
  { "name": "result-20260913-131504.txt", "sizeBytes": 3165, "mtimeIso": "…" },
  { "name": "result-20260913-120000.txt", "sizeBytes": 3165, "mtimeIso": "…" }
] }
```

Только файлы по регламенту §3.2 «ревизия». Порядок: имя по убыванию (timestamp в
имени ⇒ хронология обратная; самая свежая — первая). Это данные селектора viewer3d.

### 6.12 `GET /api/projects/<p>/archive` → скачивание zip проекта

Сервер собирает архив **на лету** (`adm-zip`, без записи на диск) и отвечает
потоком:

- Заголовки: `Content-Type: application/zip`,
  `Content-Disposition: attachment; filename="<name>-<YYYYmmdd-HHMMSS>.zip"`.
- Состав (плоские записи, без корневой папки): ВСЕ файлы проекта — редактируемые и
  ВСЕ `result-*` — **кроме**: `project.json`, поддиректории `preview/` целиком,
  любых `*.zip` (защита от вложенных артефактов).
- Пустой проект без результатов → архив хотя бы с `spec.yaml`.

Ошибки: 404. Лимит времени сборки не фиксируется (архивы локальные, десятки КБ–МБ).

### 6.13 Preview-эндпоинты

| Метод и путь | Назначение | Ответ / ошибки |
|---|---|---|
| `POST /api/projects/<p>/preview` | сохранение PNG из viewer3d; тело — сырые байты (`image/png` или `application/octet-stream`, лимит 10 МБ) | **201** `{"file":"preview-20260913-140512.png"}`; имя серверное по §3.2 (коллизия — суффиксы); создаёт `preview/` при отсутствии; 404/413 |
| `GET /api/projects/<p>/previews` | список: `{"previews":[{name,sizeBytes,mtimeIso}]}` по убыванию имени | 404; пустой список допустим |
| `GET /api/projects/<p>/preview?file=<имя>` | отдача картинки: `Content-Type: image/png`, `Cache-Control: no-cache` (файл может пересоздаваться) | имя валидируется по §3.2 «предпросмотр»; 400/404 |

## 7. Примечания к реализации API

1. Все обработчики — чистые функции `(req,res)` поверх модуля `server/workspace.ts`
   (fs-операции, шаблоны, имена) и `server/generate.ts` (spawn) — ради юнит-тестов с
   tmp-workspace (см. [05](./05-testing-acceptance.md) §3).
2. Чтение/списки файлов используют `fs.promises` + `readdirWithFileTypes`; каталог
   проекта, исчезший под ногами (удаление извне), → 404 `PROJECT_NOT_FOUND`.
3. Заголовки статики и SPA-fallback — по [01](./01-architecture.md) §3.3.

## 8. Открытые решения

1. Одинокие файлы масок с неканоническими именами (появляются после импорта, если
   спека ссылается на `blocked_basic.txt`): при первом «Сохранить в проект» редактор
   пишет канонические имена, а старые остаются в каталоге и попадают в архив.
   Авто-очистка таких осиротевших файлов — v2.
2. Политика устаревания ревизий (удаление старых `result-*`) — не входит в v1;
   история сохраняется полностью (вводная №7).
